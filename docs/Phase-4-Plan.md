# Phase 4 — restaurant cost control

## 4A: recipes and transparent cost estimates — delivered locally

Deliver Arabic **الوصفات والتكاليف** with tenant-scoped recipe drafts, revision-checked edits and immutable publication. Each recipe defines a code/name, stocked or non-stocked output, positive batch output, base output unit, effective date, optional net selling price per output unit and distinct ingredient/sub-recipe lines. Stocked output links an existing inventory material with the same unit. Definitions need units/items, but do not need a stock location to save/publish.

Support base units and validated g/kg and ml/l conversions; custom units use base quantities only. Store normalized quantities and entered units. Sub-recipes pin an exact published version. Reject tenant/reference/unit errors, self/indirect cycles, unavailable/future child versions, reused IDs and stale revisions. Bound expansion to 20 levels/1,000 nodes. Publication is serialized under the tenant lock and writes the version, dependency records, revision, audit and idempotent command receipt together. Recipe actions never post stock movements.

Use one pure resolver shared by preview/tests. The normal costing view stops at stocked sub-recipes, using their stock material cost; analytical expansion can show their raw ingredients. Root recipes always show their ingredient requirements. Display missing prices and shortages separately; known zero cost is valid and missing cost is never silently zero. Offer current remaining-stock average and latest accepted receiving price by selected location, with source/date/freshness. The latter is read from full server ledger history, not the latest-100 activity display. Show known subtotal, complete batch/per-output-unit cost, food cost percentage and gross contribution only when all costs and a positive net selling price are available. These are estimates, not finalized production allocation or net profit.

Add additive PostgreSQL recipe/version/dependency/revision tables, Dexie schema 8 recipe actions and generation-bound recovery format 11. Older archives remain readable. Upload setup before recipe saves and dependency publications before parents. Preserve rejected actions for retry/cancellation and let the user reopen the latest draft after a conflict. Include recipes in pending/review counts, tenant switching, reset generation, identity collision detection and atomic recovery. Catalog-clearing development reset removes recipes before referenced items/units; costing-method transaction reset retains definitions but clears obsolete action queues via generation.

Acceptance: version pinning, cycle/tenant/revision/date/unit protection, exact conversions and yields, stocked boundary vs analytical expansion, valid-zero/missing prices, historic latest receipt, stock-neutral posting, persistence, offline reload/dependencies/recovery/correction-by-new-action and desktop/mobile. No demo data is added to the client workspace.

Verification on 10 October 2026: 169 unit/integration tests, 31 browser/process scenarios, TypeScript, production build and offline manifest passed. Tests use isolated databases. See [Recipes walkthrough](./runbooks/Recipes.md) for the user workflow. Local branch `feat/recipe-cost-control` starts from receiving checkpoint `f3eab23`; production, sales consumption and deployment remain subsequent work.

## 4B: production and yield — delivered locally

Inventory entry point delivered on 11 October 2026: **مكونات الصنف** in the inventory setup table and optional **فتح إعداد المكونات بعد الحفظ** in the item form route into a stocked recipe for that exact output item/unit. If a definition exists, it opens for review/versioning. New definitions are prefilled and await the user's batch ingredients and save. Recipe definition does not create stock or deduct ingredients; the existing production workflow performs the physical conversion. Offline setup and existing single-level categories are retained. Verification: 202 unit/integration tests, TypeScript, production build/offline manifest and three targeted browser scenarios passed, including output-unit linkage, self-input exclusion, correct cost per output unit, offline reload, duplicate-free reopening and unchanged stock.

Plan requirements from a pinned version, capture actual inputs/usable output, consume selected-policy stock once and create stocked output at allocated cost. Treat normal loss in yield, separate abnormal waste and handle failed batches explicitly. Prove a stocked mix is consumed once without also issuing its raw ingredients.

Implement immutable `production.post` documents for stocked preparations: exact version, input/output locations, business date/reference, positive planned output, actual usable output (zero explicitly means failed batch), and one actual-input line per resolved execution material. Execution expands non-stocked children and stops at stocked children. Material quantities are base quantities, including explicit zero for unused planned ingredients; require at least one actual positive input. Changes/substitutions to the material set require a new recipe version. A batch records abnormal wasted quantity within each total issued quantity and a reason. Saving the final document offline is provisional; database acceptance posts all inputs/output, layer allocations, batch cost, audit and reserved IDs atomically. Accepted batches remain immutable; rejected actions support unchanged retry, cancellation and linked correction with fresh IDs. Accepted reversal and server-side production draft lifecycle are deferred.

Allocate each actual input using the organization policy. Successful output value equals total input value minus proportional abnormal waste value; normal yield loss creates no second deduction. A zero-output batch records all input value as failed-batch waste and creates no layer. Store exact values at twelve decimals and displayed output cost at six. FIFO outputs may use two adjacent six-decimal unit-cost layers to conserve the exact allocated value; average output blends exact value into the destination pool. Check affected stock reconciliation before and after posting, including output-at-another-location. No output material can also occur in the expanded execution inputs.

Add tenant-qualified production tables/ledger link and reference indexes, Dexie schema 9 and generation-bound recovery format 12. Setup and recipe publication synchronize first. Interleave direct receiving, legacy movements, production and transfers in capture order with dependency review; process counts after these settle and include unresolved production in count guards. Project quantities with pending inputs/output, while values remain acceptance-only. Include production in pending/review counts, switching guards, identity collision checks, reset clearing and atomic archive validation/correction chains. Keep recipe definitions on transaction reset, deleting production before catalog/recipe versions on catalog reset. Do not seed or reset client data.

Acceptance covers FIFO and average, exact fractional output conservation, zero-cost production, failed output, abnormal versus normal loss, pinned/stocked child boundaries, insufficient-stock all-line rollback, dates/units/tenant/generation/ID protection, independent reconciliation, pending capture ordering, offline reload/retry/correction/recovery, stale counts, empty setup and Arabic desktop/mobile. Non-stocked meals retain recipe estimates; sales consumption follows in 4C.

Verification on 10 October 2026: 186 unit/integration tests across 30 files, TypeScript, production build and offline manifest passed. 33 browser/process scenarios passed (31 fixture regressions plus 2 isolated empty-workspace checks). See [Production walkthrough](./runbooks/Production.md). Local branch `feat/production-yield` starts from recipe checkpoint `9baa335`.

## 4C1: menu mapping and completed sales import — delivered locally

Create tenant-scoped menu items keyed by POS source/code, with a name, active status, pinned published recipe version and quantity of recipe output represented by one sale. Source/code stay immutable after creation; revisions can change the name, version, ratio or active status without rewriting past sales. Keep this separate from the ingredient catalog.

Import bounded UTF-8 CSV files (1 MiB, 200 detail rows) through explicit column mapping: transaction ID, line ID, menu code, business date, sold quantity and total line net amount in EGP, excluding VAT and after discounts. An optional status column accepts completed sales only; require explicit confirmation. Reject unknown codes, ambiguous columns, invalid dates/quantities, refunds/voids and unmapped rows before saving. Each detail pins mapping revision, recipe version and output-per-sale. Effective dates are checked against each sale date.

Accept immutable `sales.import` documents without inventory posting. Deduplicate each external detail by tenant, source, branch, business date, transaction ID and line ID, both within a file and across files. CSV re-imports retain accepted recipe mappings even after menu edits/deactivation; new rows use current mappings. Identical repeats contribute zero new sales; changed data under an existing external key rejects the entire import. Reserve internal operation/line IDs, check mapping revisions, write new detail records/import results/audit atomically and preserve accepted history. Rejected imports support retry, cancellation and fresh-ID linked correction; accepted financial correction is deferred until refund/void workflows.

Use additive tenant-qualified tables/indexes, Dexie schema 10 and recovery format 13 for mapping actions and import documents. Setup and exact recipe publications precede mapping acceptance, then imports. Include both outboxes in session/generation checks, identity reservation, pending/review counts, switching protection and atomic recovery. Transaction resets clear sales imports while retaining menu definitions; catalog resets remove sales and menu references before recipes. No client reset, sample insertion, full POS, remote cloud change or deployment.

Acceptance: stock-neutral sales capture, source/branch/tenant/date separation, line/file/idempotency duplicates, partial overlap, changed-repeat all-line rollback, pinned history after mapping edits, zero-price sales, effective dates, revision conflicts, Arabic CSV values, offline reload/dependency order/network failure/recovery/correction and empty/mobile UI. Branch `feat/sales-import-mapping` starts from `3addd0e`.

Verification passed: 202 unit/integration tests across 33 files, 35 browser/process scenarios (33 fixture regressions plus 2 isolated empty-workspace checks), TypeScript, production build and offline manifest. See [Sales import walkthrough](./runbooks/Sales-Import.md).
