# Hosted client release — agreed scope

The **صرف مخزون** form has compact recipient/date/reference fields, item rows showing expected available and remaining stock, estimated row costs and immediate shortage warnings. The estimated total and save/cancel actions remain visible while the body scrolls. Notes expand when needed, and long documents retain paging and keyboard navigation. These are presentation changes; kitchen issues still reject shortages atomically and consume stock only on acceptance. See [stock issue form UX](./releases/stock-issue-form-ux-2026-10-12.md).

Catalog search and selection use one visible searchable combobox across receiving, waste, opening stock, purchasing, recipes, production, sales mapping and kitchen issues. Focus opens the offline catalog; typing filters names/codes, arrows/Enter choose and advance, and uncommitted searches preserve the current selection. Validation focuses the visible field and duplicate restrictions remain enforced. Menus stay outside scrolling form/table bodies. See [unified dropdown release](./releases/unified-searchable-dropdown-2026-10-12.md).

The workspace top bar exposes **اختصارات** with an Arabic keyboard guide, and all editors show compact hints. Shared navigation uses Enter/Shift+Enter for fields, Ctrl/Command+Enter for explicit validation/save and Alt+Insert for available row additions. Multiline input and disabled confirmations keep their native/guarded behavior. See [forms walkthrough](./runbooks/UI-Forms.md) and [keyboard release](./releases/form-keyboard-2026-10-12.md).

Kitchen 1, Kitchen 2 and similar recipients use **صرف المطابخ** documents. **إدارة المطابخ** supports adding, renaming, deleting from future selection and restoring recipients, while preserving accepted history. Every issued material is immediately consumed from the source warehouse on acceptance, with FIFO/moving-average cost and no receiving-kitchen balance. The keyboard form supports multiple materials, automatic search-result dropdowns, validation, offline capture, linked rejected-document corrections, print/PDF and filtered/paginated history. Kitchen shortages reject atomically; sales retain their separately agreed partial-deduction behavior. Existing recipe selections are not changed. See [Kitchen issues](./runbooks/Kitchen-Issues.md).

The first hosted organization is واحة أولاد سعد (Wahat Awlad Saed). Its name, enhanced logo and public contact profile are tenant data; FooDo is the shared platform identity with the [accepted brand assets](./branding/FooDo.md). Click المؤسسة الحالية to open the details dialog; the home page keeps its operational overview. Initial owner login: test@fodo.com. Tenant isolation remains part of the architecture; subscription billing, membership administration and separate demo environments are deferred.

New sales imports deduct only materials selected in the accepted sale's pinned recipe version (`salesStockItemIds`). An empty or omitted selection keeps calculation-only behavior. Reports calculate every theoretical ingredient, respecting stocked preparation boundaries. All ingredients remain in estimated recipe cost, including unselected materials. Costs use the selected current stock-average or latest-receipt basis, with missing prices shown explicitly; full recipe cost remains an estimate. The accepted import separately records the actual quantity and FIFO/moving-average value issued for selected materials.

Shortages do not reject otherwise valid sales. Deduct the available quantity of each selected material and save required, deducted and missing quantities in the accepted import. Highlight shortage rows in preview and history. Preserve non-negative inventory and reconciled layers/ledger values. Later receiving or balance corrections do not automatically backfill an earlier shortage, and exact repeats never deduct again. Invalid mappings, identity conflicts, unauthorized requests or corrupt stock reconciliation still reject atomically. Existing sales and published versions stay unchanged.

The inventory table exposes **تعديل الرصيد** for an active material at the selected location. A one-item form captures the new non-negative balance, required reason and explicit unit cost for any increase, with known cost offered as a suggestion. Save a linked single-line count definition and finalization together in the local outbox; the server's existing count engine posts their delta, valuation and audit actor. Preserve the old/new quantities and reject stale location checkpoints. Reuse existing review/recount/cancel and recovery flows. Do not update a balance row directly or reset client data. See [stock balance editing](./runbooks/Stock-Balance-Editing.md).

Cloudflare serves the shared React workspace and same-origin authenticated API. Supabase Auth supplies real accounts and managed Postgres stores tenant data behind an authenticated Edge Function. Browser tokens stay in secure HTTP-only cookies. Hosted routes reject development sessions and costing resets. The hosted interface excludes development notices, fixture-company switching and destructive controls. Local development keeps its existing launcher and database.

Use a new feature branch from the verified local checkpoint. Type-check, test shared business rules and auth boundaries, build the hosted bundle and publish through the connected accounts. The stock-balance/sales update reused the organization, owner account and schema without provisioning. The later temporary trial adds a private administrative backup table and deny policy through new migrations; retain earlier applied migrations. Record actual deployment identifiers and URLs after verification. Never commit credentials, generated owner passwords, local databases or cloud build output. Push the reviewed feature branch and open a PR; deployment does not imply merging main.

Initial provisioning copied the approved 328-item catalog with zero balances into the hosted organization. The user has subsequently approved temporary menu-based stock and operations in that same workspace. The trial uses fictional prices, recipes and quantities; its private baseline backup and guarded cleanup restore the original catalog before real operations start. See [temporary client data](./runbooks/Temporary-Client-Data.md). Do not copy unrelated development transactions, sessions or secret keys.

Offline capture uses the existing tenant-bound Dexie outboxes and generation checks. First login and server acceptance require connectivity. A saved workspace has a bounded 24-hour offline grant; expired grants retain queued work and require sign-in. Signing out locks the workspace and retains pending work for the same account.

Release checks include unauthenticated/cross-tenant/origin rejection, duplicate-safe posting, sign-in/refresh/sign-out, no development/reset routes or notes, recipe cost completeness, unchanged stock for unselected materials and legacy recipes, FIFO/moving-average selected deductions, accepted partial/zero-stock shortages, pinned versions, stale balance edits, reload/offline capture and recovery. Cloud Auth/storage integration must be verified with real requests before sharing the client URL. Run destructive or stock-writing browser scenarios against isolated fixture data, never the client's catalog.
