# سجل تسليم مشروع Fodo وقرارات المحادثات — 1 نوفمبر 2026

هذا الملف هو نقطة البداية عند استكمال المشروع من جهاز أو محادثة جديدة. وهو يلخص نتائج محادثات المشروع وقراراتها العملية، ويربطها بالمستندات التفصيلية الموجودة في المستودع. لا يحتوي على كلمات مرور أو رموز وصول أو بيانات بصمات أو بيانات موظفين.

## 1. ترتيب مصادر الحقيقة

عند وجود اختلاف بين مستند قديم والكود الحالي، استخدم الترتيب التالي:

1. قاعدة البيانات الحية ونتيجة `/api/v1/health` لتحديد النسخة المنشورة وحالة البيانات الفعلية.
2. الكود والاختبارات في الفرع الحالي.
3. هذا السجل للقرارات المعتمدة وحالة التسليم.
4. أدلة التشغيل في `docs/runbooks/`.
5. سجلات الإصدارات في `docs/releases/`؛ فهي شواهد تاريخية وليست دائمًا وصفًا للنسخة الأحدث.
6. الخطط المرحلية القديمة؛ لا تعيد تنفيذ بند منها إذا كان الكود أو دليل تشغيل أحدث قد تجاوزه.

أي حذف لبيانات العميل أو استبدال لواجهة خلفية أو نشر لقاعدة البيانات يحتاج فحص الحالة الحية وموافقة صريحة جديدة. لا يُعاد تنفيذ حذف ورد في محادثة قديمة لمجرد أنه مذكور هنا.

## 3. هدف المنتج ونطاقه الحالي

Fodo نظام عربي RTL لإدارة مخزون المطاعم والتكلفة والوصفات والمطابخ والإنتاج. وحدة العمل الأساسية للعميل الحالي هي «واحة أولاد سعد»، مع مخزن رئيسي ومطابخ ومواقع مخزون مستقلة. النظام يدعم العمل دون اتصال، مزامنة أوامر idempotent، سجل مراجعة، استرداد، وطباعة/تصدير.

النطاق المنفذ يشمل:

- تعريف المواد والوحدات والموردين والمواقع والمطابخ ونقاط البيع.
- الرصيد الافتتاحي، الاستلام المباشر، المشتريات والاستلام الجزئي، مرتجعات الموردين، التحويلات والجرد والتسويات.
- الوصفات والإصدارات، تقدير التكلفة، الإنتاج والتحضير، المطبخ المركزي والجزارة.
- صرف المخزن إلى المطابخ والاستلام الجزئي ومتابعة المتبقي بالطريق.
- المبيعات والاستيراد وPOS وشاشة المطبخ والمصروفات والتصحيحات والتقارير.
- Offline outbox والمزامنة ومراجعة المرفوضات وملف الاسترداد.
- الاستيراد والتصدير والطباعة وواجهة عربية قابلة للعمل بلوحة المفاتيح.

## 4. قرار تكلفة المخزون

القرار المعتمد هو **المتوسط المرجح المتحرك** كطريقة افتراضية، وليس FIFO. يبقى FIFO خيارًا متاحًا من إعداد المخزون للاختبارات أو المنظمات التي تختاره صراحة.

- الاستلامات والزيادات المسعرة تضيف كمية وقيمة إلى متوسط المادة في الموقع.
- الصرف والهالك والعجز والتحويل يستهلك وفق سياسة المنظمة عند قبول الخادم.
- التكلفة النهائية لا تعتمد على القيمة المعروضة محليًا قبل المزامنة.
- أسعار مصادر الشراء تبقى مرجعًا تاريخيًا ولا تتغير بسبب المتوسط.
- تغيير طريقة التكلفة في بيئة التطوير يمسح معاملات المخزون ويغير generation؛ لا يُستخدم في العميل الحي دون موافقة واضحة.

التفاصيل: [Costing-Methods.md](runbooks/Costing-Methods.md).

## 5. الوصفات والتكلفة المعيارية

قرارات الوصفات المعتمدة:

- أكواد المواد والوصفات والدفعات والعمليات تُولد تلقائيًا حيث تدعم النماذج ذلك، ولا يطلب من المستخدم اختراع مرجع يدوي غير ضروري.
- الوصفة المنشورة إصدار غير قابل للتعديل؛ التغيير ينتج مسودة إصدار جديد ثم إصدارًا منشورًا جديدًا.
- تكلفة الوصفة الافتراضية تستخدم **متوسط المخزون المتبقي** في الموقع.
- «آخر سعر استلام» يبقى مصدر مقارنة اختياريًا ولا يحل محل المتوسط افتراضيًا.
- عند غياب تكلفة أي مكوّن تعرض الوصفة **تكلفة غير مكتملة**؛ لا يعتبر المكوّن مجانيًا أو صفرًا تلقائيًا.
- كل المكونات تدخل في تقدير التكلفة. تحديد «يُخصم عند البيع» يحدد فقط ما يخصم عند قبول المبيعات الجديدة.
- إذا كان الناتج تحضيرًا مخزنيًا مثل الكفتة أو السجق، تخصم مكوناته عند الإنتاج، ثم يخصم الناتج نفسه عند البيع؛ لا تخصم الخامات مرة ثانية عند البيع.
- المقارنة بين التكلفة المعيارية والفعلية منفذة لدفعات المطبخ المركزي باستخدام لقطة إصدار الوصفة المثبتة في الدفعة.

التفاصيل: [Recipes.md](runbooks/Recipes.md) و[Production.md](runbooks/Production.md).

## 6. المطبخ المركزي والجزارة

### المسار التشغيلي المعتمد

`المخزن الرئيسي → إنتاج قيد التنفيذ → استلام فعلي محجوز → إغلاق وتثبيت التكلفة → مخزون متاح → المطابخ`

أمين المخزن يسجل الصرف والاستلام الفعلي. لا يلزم حساب مستخدم منفصل للمطبخ المركزي في هذه المرحلة.

### القواعد المنفذة

- الدفعة قد تكون جزارة أو تحضيرًا أو تصنيعًا، وقد ترتبط بوصفة كفتة أو سجق أو تُسجل بمواد فعلية دون وصفة.
- يمكن وجود عدة مدخلات وعدة مخرجات، وصرف إضافي بعد إعادة فتح الدفعة.
- يخصم المخزون **عند قبول صرف المكونات** مرة واحدة؛ إنشاء الدفعة لا يخصم شيئًا، واستلام الناتج لا يعيد خصم المكونات.
- نموذج الدفعة الجديدة ونموذج الصرف يعرضان الرصيد المؤكد، المتاح بعد العمليات المحلية، المطلوب، والعجز لكل مكوّن.
- يمكن حفظ خطة الدفعة مع وجود عجز، لكن لا يمكن تأكيد الصرف حتى يُعالج العجز.
- الاستلام الجزئي مسموح. المنتج المستلم يبقى «محجوزًا» وغير قابل للصرف حتى إغلاق الدفعة وتثبيت تكلفته.
- المرتجع غير المستخدم يعود بتكلفة مصادر الصرف الأصلية.
- الفاقد الطبيعي يدخل في تكلفة الناتج، والفاقد غير الطبيعي يبقى مصروفًا منفصلًا.
- تكاليف التشغيل تدخل في تكلفة الدفعة، والتوزيع بين عدة مخرجات يجب أن يساوي 100%.
- موازنة الوزن تجمع الوحدات المتوافقة فقط. رسالة الخطأ تعرض الآن المدخلات والمستلم والمرتجع والفاقد والفرق وما يلزم لمعالجته؛ الأعداد ليست أوزانًا تلقائيًا.
- المنتجات لا تصبح متاحة للتحويل للمطابخ قبل إغلاق الدفعة، وهو قرار المرحلة الأولى لتجنب تغيير تكلفة منتج سبق صرفه.
- الاستلام والمرتجع والفاقد وتكلفة التشغيل يمكن تصحيحها بإجراء مرتبط. الإلغاء المالي يتم بعكس مرتبط يحفظ الأصل والتدقيق، وليس حذف الحركة المقبولة.
- الإغلاق يمنع الرصيد غير المفسر أو التوزيع الناقص أو التكرار، ويثبت تكلفة المنتجات المحجوزة.
- المقارنة المعيارية/الفعلية تعرض فرق المواد وتكاليف التشغيل والانحراف.

التفاصيل: [Central-Kitchen.md](runbooks/Central-Kitchen.md)، [central-kitchen-2026-10-29.md](releases/central-kitchen-2026-10-29.md)، و[central-kitchen-ux-2026-10-29.md](releases/central-kitchen-ux-2026-10-29.md).

### نقطة غير مكتملة بالكامل

لا تزال شاشة «الإنتاج والتحضير» العامة وشاشة «المطبخ المركزي والجزارة» مسارين ظاهرين في الواجهة. الدليل داخل التطبيق يوجه إنتاج الوصفات إلى المطبخ المركزي، لكن إزالة المسار القديم أو دمجه نهائيًا لم تكتمل. يجب توحيدهما دون فقد حالات الإنتاج القديمة أو تقاريرها، ثم ترحيل الاختصارات والدليل والاختبارات إلى مسار واحد.

## 7. الجزارة التقليدية

- تجهيز الضاني والبقري القديم محفوظ داخل تبويب «تجهيز البقري والضاني» ولا تُحذف بياناته أو تقاريره تلقائيًا.
- يمكن للمطبخ المركزي إنتاج وصفات لحم مركبة مثل الكفتة والسجق باستخدام اللحم وباقي مكونات المخزن.
- تقارير الجزارة تعرض المردود والتكلفة وتوزيع تكلفة المخرجات.
- حقول رؤوس الضاني والوزن الحي ومخرجات التقطيع تبقى متاحة في العمليات المناسبة.

## 8. المخزون والنماذج الأخيرة

آخر قرارات الواجهة المنفذة:

- نموذج «مستند رصيد افتتاحي جديد» مستقل عن «استلام مواد»، لكنه يستخدم نفس نمط UX الأفقي والمدخلات الواضحة.
- مرجع الرصيد الافتتاحي اختياري.
- الرصيد الافتتاحي المقبول قابل للتصحيح عبر التدفق المخصص مع الحفاظ على السجل، وليس بتعديل صامت للحركة الأصلية.
- نموذج إضافة المادة يدعم «حفظ وإضافة مادة جديدة» دون إغلاق النموذج.
- استيراد قائمة المواد والأرصدة الافتتاحية من ملف spreadsheet متاح مع معاينة وتحقيق قبل الحفظ.
- تصدير المواد إلى Excel متاح.
- أزرار الاستيراد موجودة في رأس النموذج بدل استهلاك مساحة قائمة المواد.
- نماذج المواد والرصيد الافتتاحي والاستلام وصرف المطبخ مصممة أفقيًا على سطح المكتب؛ لا تعاد إلى أعمدة رأسية ضيقة.
- رؤوس الأقسام والتنبيهات والتذييل مضغوطة لزيادة ارتفاع قائمة المواد، مع بقاء أهداف اللمس مناسبة على الهاتف.
- تفاصيل المادة الأساسية تستخدم خطًا أوضح وتسلسلًا بصريًا أقوى.
- رسائل التحقق تظهر بجوار الحقول دون ضغط اختيار المادة والكمية والتكلفة في عرض غير صالح.

الـcommits الرئيسية لهذه الجولة: `d4f86ce`، `cf341cd`، و`491c52f`.

## 9. التحويلات والمطابخ والمبيعات

- تحويل المخزن إلى مطبخ يخصم من المصدر عند الإرسال ويتابع الكمية والقيمة بالطريق.
- الاستلام الجزئي يبقي المتبقي Outstanding، وفاقد الطريق يسجل صراحة.
- قيمة التحويل المقبولة تصل للموقع الجديد ثم تدخل في متوسطه إن كانت المنظمة تستخدم المتوسط.
- سعر مستند الصرف للمطبخ مستقل عن التكلفة الفعلية للمخزون، ويظهر في المستند والتقارير دون إعادة تسعير المخزون.
- كل POS مرتبط بمطبخ؛ المبيعات الجديدة تخصم المواد المحددة في إصدار الوصفة من مخزون ذلك المطبخ.
- العجز لا يجعل الرصيد سالبًا: تخصم الكمية المتاحة، تحفظ الكمية الناقصة، وتقبل المبيعات مع إبراز العجز.
- التحضير المخزني يخصم الناتج عند البيع، بينما مدخلاته خُصمت سابقًا عند الإنتاج.

التفاصيل: [Transfers.md](runbooks/Transfers.md)، [Kitchen-Issues.md](runbooks/Kitchen-Issues.md)، [Sales-Import.md](runbooks/Sales-Import.md)، و[Counter-POS.md](runbooks/Counter-POS.md).

## 10. Offline والمزامنة والاسترداد

- المتصفح يحفظ الأوامر المحلية في IndexedDB/outbox؛ الواجهة المحلية ليست مصدر الرصيد النهائي.
- الخادم يعيد فحص المخزون وrevision وgeneration والهوية داخل معاملة واحدة.
- operation IDs تجعل إعادة المحاولة idempotent ولا تكرر الخصم أو الاستلام.
- العمليات المرفوضة تذهب للمراجعة ويمكن إعادة إرسالها أو تصحيحها أو إلغاؤها حسب نوعها.
- ملف الاسترداد ينقل الأوامر غير المتزامنة بعد المعاينة والتحقق من المنظمة والجيل والتوقيع/المنحة.
- مزامنة المحادثة أو نسخ Git لا ينقل IndexedDB. قبل تبديل الجهاز يجب مزامنة كل العمليات أو تصدير ملف استرداد.

تفاصيل الاستخدام: [UI-Forms.md](runbooks/UI-Forms.md) و[Recipes.md](runbooks/Recipes.md).

## 11. البيانات التجريبية وعمليات الحذف

خلال التطوير استُخدمت بيانات تجريبية، وأُعطيت تعليمات بمسح معاملات إنتاج ومخزون ثم تعليمات أوسع لمسح أرصدة وحركات وأصناف ووصفات لواحة أولاد سعد. كما أُعيد إدخال مواد وأرصدة ووصفات في مراحل أخرى. لذلك:

- **لا تفترض حالة البيانات الحية من سجل المحادثة أو fixtures.** افحص tenant الحي قبل أي عمل.
- لا تعيد تشغيل reset أو حذف catalog بناءً على هذه الفقرة.
- لا تستخدم `SAAS_DEMO_MODE` أو `development_empty_baseline` على البيئة الحية.
- أي حذف جديد يجب أن يسرد الجداول/الكيانات المتأثرة، العلاقات التابعة، طريقة النسخ الاحتياطي، وإمكانية الاسترداد، ثم يحصل على موافقة صريحة.
- ملفات Excel والأسعار التي قدمها المستخدم كانت مصادر إدخال وليست مواصفات دائمة. البيانات الفعلية داخل النظام هي المرجع بعد القبول.

## 12. HR وجهاز البصمة K14 Pro

النطاق الذي نوقش للمرحلة الأولى هو **ملفات الموظفين والحضور فقط من جهاز البصمة**. لا توجد حاجة حاليًا إلى الرواتب أو الصلاحيات أو استيراد سجل تاريخي قديم.

المتوفر في الكود أدوات تشخيص ونسخ احتياطي محلي في `helpers/attendance-diagnostic/`:

- الجهاز: ZKTeco K14 Pro.
- العنوان الذي ظهر أثناء التشخيص: `192.168.123.201` والمنفذ `4370`.
- تفحص الشبكة ووجود `zkemkeeper` أو fallback تشخيصي محدود.
- أداة التشخيص الأصلية لا تنزل البصمات. أداة `Backup-K14SelectedData.ps1` الإضافية تنزل المستخدمين المختارين وقوالبهم إلى ملف محلي حساس؛ لا ترفعها إلى Fodo.
- يدعم Communication Key اختياريًا، لكن لا يجب حفظ المفتاح في Git أو هذا المستند.

ما لم يُنفذ بعد:

- وحدة HR داخل Fodo.
- مزامنة الموظفين والحضور من الجهاز.
- agent محلي دائم يقرأ الجهاز ويرسل أحداث الحضور إلى السحابة.
- قواعد الورديات، التأخير، الغياب أو التقارير.

**تحديث منفذ في 1 نوفمبر 2026:** بموافقة المستخدم جرى حفظ نسخة كاملة ثم استبدال بيانات الجهاز. النتيجة المتحققة: 65 مستخدمًا بالأكواد 101–165، و101 قالب بصمة لـ51 مستخدمًا، و14 مستخدمًا بانتظار تسجيل بصماتهم. مُسح الحضور القديم، وأعيد تمكين الجهاز. 95 قالبًا مطابقًا بايتًا ببايت؛ الستة الأخرى تحتفظ بكل البايتات الأصلية وتضيف ستة أصفار في النهاية. استُخدمت أسماء إنجليزية على الجهاز بعد أن أعاد SDK الأسماء العربية كعلامات استفهام. اختبار إصبع موظف فعلي ما زال ينتظر تأكيد المستخدم. لا تعد تنفيذ المسح.

الشيفتات مؤجلة بطلب المستخدم. حركات 1 نوفمبر قبل المسح عُرضت في المحادثة فقط: 50 حركة، منها 45 مرتبطة بالأكواد الجديدة و5 تحتاج مطابقة. لم تُعد إلى الجهاز أو Fodo. تفاصيل التسليم دون بيانات شخصية: [Device-Migration-2026-11-01.md](Device-Migration-2026-11-01.md).

قبل أي مسح للجهاز يجب أخذ backup من برنامج ZKTeco العامل، اختبار استعادته، فصل السجلات المطلوبة، ثم تنفيذ المسح يدويًا بموافقة واضحة. لا يُعرض منفذ 4370 على الإنترنت.

## 13. المصادقة والنشر

- التطبيق الحي يستخدم تسجيل دخول مستضاف، ولا يوجد signup عام أو password reset ذاتي في هذه المرحلة.
- زر تسجيل الخروج أضيف في commit `9b2be01`.
- Cloudflare Worker يقدم الواجهة، وSupabase يقدم Auth/PostgreSQL/واجهة الخادم الحية.
- نشر الواجهة لا يعني نشر Supabase أو تغيير schema. لا تستبدل Edge Function أو تنفذ migration إلا عندما تتطلب الميزة ذلك وبعد مراجعة منفصلة.
- لا تضع مفاتيح أو cookies أو tokens في المستودع أو مستند التسليم.

### فحص وبناء الواجهة

```powershell
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build:cloud
```

### نشر Cloudflare

سجل الدخول أولًا على الجهاز الجديد، ثم ابنِ الحزمة المعزولة وانشر من ملفها فقط:

```powershell
pnpm exec wrangler login
pnpm build:cloud
pnpm exec wrangler deploy --config .cloud-build/publish/wrangler.json
```

لا تنشر `.cloud-build/wrangler.json` المختلط ولا تستخدم `--no-bundle` من مجلد إداري. بعد النشر افحص:

```text
https://fodo.am-agent2026.workers.dev/api/v1/health
```

ثم طابق `buildVersion` مع ناتج البناء، وافحص أن Worker الحالي يحتفظ بالbindings والإعدادات المطلوبة.

التفاصيل: [Hosted-Release.md](Hosted-Release.md) و[Developer-Guide.md](Developer-Guide.md).

## 14. الانتقال إلى جهاز جديد

اتبع دليل [Move-To-New-Laptop.md](Move-To-New-Laptop.md). لا تعتمد على نسخ مجلد worktree الحالي وحده؛ ملف `.git` يشير إلى الجهاز القديم. حزمة النقل الخاصة تحتوي Git bundle مستقلًا وملفات العمل المحلية المهمة.

على الجهاز الجديد:

```powershell
git clone https://github.com/3azam0/Sas.git
cd Sas
git switch --track origin/codex/recipe-forms-compatibility
corepack enable
corepack prepare pnpm@11.25.0 --activate
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
```

ثم:

- ثبت Codex Desktop وسجل الدخول بنفس حساب OpenAI ومساحة العمل.
- سجل الدخول إلى GitHub وCloudflare من جديد؛ لا تنقل `auth.json` أو credential stores.
- أعد ربط Supabase فقط إذا احتجت إدارة backend.
- انسخ ملفات العمل الأصلية خارج Git مثل spreadsheets أو backups أو exports المطلوبة.
- لا تنقل `node_modules` أو `.data-browser-*` أو browser cache.
- قواعد `.data-dev` و`.data-central-preview` وملفات الاختبار بيانات محلية متجاهلة؛ لا تنقلها إلا إذا كانت هناك حاجة محددة لحالة تجريبية، وبعد إيقاف السيرفر.
- قبل ترك الجهاز القديم، تأكد من عدم وجود outbox معلق أو صدّر Recovery archive.

هذا السجل وGit history بديل كافٍ عن نقل محادثات Codex للعمل الهندسي. المحادثات تبقى أرشيفًا إضافيًا فقط.

## 15. أولويات العمل التالية

1. على الجهاز الجديد: clone الفرع، تشغيل typecheck/tests/build، ثم التحقق من التطبيق الحي دون تعديل بيانات.
2. إجراء الفحص المرئي المؤجل لكل نماذج المخزون والمطبخ المركزي على desktop/mobile وإصلاح أي overflow أو ضغط حقول.
3. توحيد «الإنتاج والتحضير» و«المطبخ المركزي والجزارة» في دورة واحدة، مع إبقاء قراءة التاريخ القديم والتقارير.
4. اختبار قبول كامل لدفعة كفتة متعددة المكونات: صرف، صرف إضافي، استلام جزئي، مرتجع، فاقد، تكلفة تشغيل، إغلاق، ثم تحويل جزئي لمطبخ.
5. التحقق من المتوسطات والقيم المحجوزة وOutstanding بعد الإغلاق والتحويل، ومن رسائل موازنة الوزن والعجز.
6. مراجعة الفرع وفتح PR/دمجه إلى `main` عند القبول؛ النشر الحالي لا يعني أن الفرع مدمج.
7. إذا أُعيد فتح HR: ابدأ بوثيقة نطاق وagent محلي وآلية مطابقة Employee ID؛ لا تبدأ بمسح جهاز البصمة.
